# Architecture

The library's architecture has three layers: **Storage** holds content on the filesystem, **Indexing** enables retrieval through multiple strategies, and **Coordination** connects agents through shared state. Three agents operate across these layers — see `agents.md` for their roles and specifications.

## Storage

The canonical store is the filesystem, Git-versioned.

| Folder | Contents |
|--------|----------|
| `/inbox/` | Raw material. Each item is a Markdown file with frontmatter (title, source URL, tags, file type, etc.). For links and text, content lives in the MD body. For files and artifacts (PDFs, images, binaries), a registration MD file points to the artifact stored alongside it (future: external storage like S3). Items stay here permanently. |
| `/nuggets/` | AI-synthesized insights. Flat folder of Markdown files with frontmatter (title, maturity, tags, sources, etc.). No subfolders. Every entry is generated by the librarian through cross-source synthesis. Discovery is through tags and embeddings. |
| `/meta/` | Governance and design documents — vision, architecture, schemas, agent roles, quality policies, technology decisions, and design principles. These shape how the library and its agents operate but are not library content: they are not indexed, not ingested into `/inbox/`, and not synthesized into `/nuggets/`. Human-owned — agents read from `/meta/` for guidance but do not write to it. |

No database is required for content storage — a database (SQLite/PostgreSQL) is a future migration path when file-based storage becomes a bottleneck.

## Indexing

### Indexes

Multiple indexes over the same data, each optimised for a different retrieval pattern:

- **Vector index:** embeddings of each entry for semantic similarity search.
- **Tag index:** flat labels for filtering (e.g. "python", "auth", "2024", "stale").
- **Provenance index:** nugget `sources` fields link back to raw items and other nuggets for traceability.

### Views

Read-only views of the underlying data for different purposes. A folder tree view, a mind-map view, a dependency graph, a dashboard of library health metrics. These are generated from queries, not manually maintained.

## Coordination

Agents coordinate through the filesystem and ChromaDB. Each agent reads from files, performs its work, writes results back to files, and updates embeddings in ChromaDB. No agent calls another directly — they discover each other's work by reading shared state. This decouples agents completely — they can run on different machines, different schedules, or different LLM providers.

### Example Flow

A user drops a URL into `/inbox/`. The indexer picks it up, catalogues the raw item with metadata (title, tags, source URL), and generates an embedding. The librarian, on its next scheduled run, scans catalogued raw items and discovers that this new article covers ground related to two existing raw items. It synthesizes a nugget that captures the cross-source pattern — an insight that doesn't exist in any single source — and stores it in `/nuggets/` with all three source IDs in the nugget's `sources` field. On subsequent runs, the librarian revisits the nugget for deeper analysis, expands the synthesis into standalone prose, and discovers related nuggets via vector similarity. After completing this refinement cycle, the librarian presents a summary to the user: "Created 1 nugget from 3 sources, enriched 2 existing nuggets. Want to update governance or agent configs?" The user reviews and decides. Later, an agent asks the retriever "what do we know about event-driven architecture?" The retriever runs a vector search across both raw items and nuggets, finds the synthesized nugget among the results, and returns a concise summary with its maturity level. The retriever can also read the nugget's `sources` field to surface the original source material if deeper context is needed.

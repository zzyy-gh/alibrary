# Architecture

The library's architecture has three layers: **Storage** holds content on the filesystem, **Indexing** enables retrieval through multiple strategies, and **Coordination** connects agents through a shared event queue. Four agents operate across these layers — see `agents.md` for their roles and specifications.

## Storage

The canonical store is the filesystem, Git-versioned.

| Folder | Contents |
|--------|----------|
| `/inbox/` | Raw material. Each item is a Markdown file with frontmatter (title, source URL, tags, file type, etc.). For links and text, content lives in the MD body. For files and artifacts (PDFs, images, binaries), a registration MD file points to the artifact stored alongside it (future: external storage like S3). Items stay here permanently. |
| `/nuggets/` | AI-synthesized insights. Flat folder of Markdown files with frontmatter (title, maturity, tags, quality_score, decay_rate, sources, etc.). No subfolders. Every entry is generated by the indexer or librarian. Discovery is through tags and embeddings. |
| `/meta/` | Governance and design documents — vision, architecture, schemas, agent roles, quality policies, technology decisions, and design principles. These shape how the library and its agents operate but are not library content: they are not indexed, not ingested into `/inbox/`, and not synthesized into `/nuggets/`. Human-owned — agents read from `/meta/` for guidance but do not write to it. |

No database is required for content storage — a database (SQLite/PostgreSQL) is a future migration path when file-based storage becomes a bottleneck.

## Indexing

### Indexes

Multiple indexes over the same data, each optimised for a different retrieval pattern:

- **Vector index:** embeddings of each entry for semantic similarity search.
- **Tag index:** flat labels for filtering (e.g. "python", "auth", "2024", "stale").
- **Provenance index:** nugget `sources` fields link back to raw items and other nuggets for traceability.

### Views

Read-only views of the underlying data for different purposes. A folder tree view, a mind-map view, a dependency graph, a dashboard of library health metrics. These are generated from queries, not manually maintained.

## Coordination

The agents follow a shared-filesystem-plus-event-queue pattern. The filesystem is the library itself. Each operational agent reads from the files, performs its work, writes results back to files, and emits events to the SQLite event queue. The intern reads everything but writes only to the recommendations queue. No agent calls another directly. This decouples them completely — they can run on different machines, different schedules, or different LLM providers.

### Event Queue

A SQLite table where agents post events and consume tasks. Events are typed and carry a payload:

| Event | Emitted By | Description & Payload |
|-------|------------|----------------------|
| ingest:received | Inbox watcher | New item detected in `/inbox/`. Payload: file path, file type, timestamp. Triggers the indexer. |
| raw:catalogued | Indexer | Raw item has been catalogued with metadata. Payload: raw item ID, file path, tags. |
| entry:created | Librarian | New nugget synthesized from cross-source patterns. Payload: entry ID, source IDs. |
| entry:enriched | Librarian | Entry maturity upgraded. Payload: entry ID, old/new maturity. |
| entry:merged | Librarian | Duplicate entries merged. Payload: surviving ID, merged IDs. |
| entry:consolidated | Librarian | Related entries consolidated into higher-level nugget. Payload: new nugget ID (absorbed IDs listed in nugget's `sources` field, originals marked stale). |
| entry:stale | Librarian | Entry flagged as potentially outdated. Payload: entry ID, reason. |
| link:broken | Librarian | Source URL no longer accessible. Payload: entry ID, URL, HTTP status. |
| knowledge:gap | Researcher | Query could not be satisfied. Payload: original query, domain, attempted strategies. |
| review:needed | Librarian | Entry past its review-by date. Payload: entry ID, days overdue. |
| intern:recommendation | Intern | A new recommendation has been posted to the review queue. Payload: recommendation type, target entry/policy, rationale, suggested action. |

### Example Flow

A user drops a URL into `/inbox/`. The indexer picks it up, catalogues the raw item with metadata (title, tags, source URL), generates an embedding, and emits "raw:catalogued". The librarian, on its next scheduled run, scans catalogued raw items and discovers that this new article covers ground related to two existing raw items. It synthesizes a nugget that captures the cross-source pattern — an insight that doesn't exist in any single source — stores it in `/nuggets/` with all three source IDs in the nugget's `sources` field, and emits "entry:created". On subsequent runs, the librarian revisits the nugget for deeper analysis, expands the synthesis into standalone prose, discovers related nuggets via vector similarity, and emits "entry:enriched". After completing this refinement cycle, the librarian presents a summary to the user: "Created 1 nugget from 3 sources, enriched 2 existing nuggets. Want to update governance or agent configs?" The user reviews and decides. Later, an agent asks the researcher "what do we know about event-driven architecture?" The researcher runs a vector search across both raw items and nuggets, finds the synthesized nugget among the results, and returns a concise summary with a confidence score. The researcher can also read the nugget's `sources` field to surface the original source material if deeper context is needed. Meanwhile, the intern observes across all of this: query patterns, synthesis quality — and periodically posts recommendations for how the system can improve.

Dynamic workspace orchestration

Architecture for multi-workspace AI agent systems where process and product stay coherent

Core invariant: A workspace is a paired guarantee — the workflow guidelines and the outputs always belong to each other. If a task would break that pairing, spin up a new workspace rather than contaminate an existing one.

The architecture

The orchestrator lives outside all workspaces. It has its own guidance file that tells it how to discover workspaces, read their registries, and decide routing. Workspaces are storage — each one pairs a workflow (how to work here) with outputs (what was produced here). The runtime is dynamic: any session — yours or the orchestrator's — spawns agents into workspaces on demand.

The three layers

The key distinction is between what's stored on disk and what's actively running. Everything on disk is passive — a session (yours or the orchestrator's) brings it to life. Anyone can enter a workspace and start a session there.

Layer What it contains Who can modify it Who can start a session here
Orchestrator Its own CLAUDE.md (how to orchestrate), workflows, registry, examples You (design the workflows) You or a scheduler — the orchestrator reads its guidance, then spawns agents into workspaces
Workspace Workflow (CLAUDE.md + skills + agents) paired with outputs You (workflow), agents (outputs) You directly (cd workspace && claude) or orchestrator via query(cwd=...)
Runtime An active agent session — ephemeral, exists only while running The running agent Started by whoever initiated the session — the coherence rules apply regardless of who started it
The workspace doesn't care who started the session. Whether you cd into it and run Claude Code directly, or the orchestrator spawns a subagent via the Agent SDK — the same CLAUDE.md loads, the same skills are available, and the same coherence invariant applies. The orchestrator is just one way in. You are another. The rules don't change.

Orchestrator anatomy

The orchestrator is unique because it has its own guidance file but produces no mission outputs. Its CLAUDE.md tells it how to behave as an orchestrator — not how to do research, writing, or coding.

The orchestrator's CLAUDE.md covers:

• Discovery — how to find and read workspace CLAUDE.md files, scan for skills, understand what each workspace does
• Registry — a manifest of all known workspaces, their domains, their declared cross-references
• Routing rules — when to spawn into an existing workspace, when to ask the user, when to create a new workspace
• Coherence enforcement — how to detect undeclared cross-references and what to do about them
• Workflow templates — recipes for multi-workspace tasks (e.g., "research then write" as a sequence of spawns)

Workspace anatomy

Every workspace has two halves that must stay paired. The workflow defines how work is done here. The outputs are what was produced here. The pairing is the point — you can read a workspace's workflow and know exactly what kind of outputs belong here and how they were produced.

Workflow = CLAUDE.md + skills + agents + declared references. This is the "how" — how work gets done here, what standards apply, what external skills are available.

Outputs = findings, drafts, src, articles. This is the "what" — the actual products of work. These must always be governed by the workflow they sit alongside.

Cross-referencing vs contamination

A workspace that declares cross-references in its workflow (like Article Pipeline referencing Researcher and Writer skills) is clean by design. The workflow explicitly says "I use these external skills," so outputs produced under that workflow are coherent — they were made with full awareness of the combined process.

The danger is undeclared references: an agent working in the Researcher workspace suddenly needing Writer skills that aren't in Researcher's workflow. If it proceeds, the outputs (writing artifacts in findings/) are orphaned — governed by no workflow. The orchestrator's job is to catch this before it happens.

Decision rules

Rule 1
Declared refs → run
If a workspace's workflow explicitly references skills from other workspaces, run confidently. The outputs are governed by a workflow that knows about the dependency.
Rule 2
Undeclared refs → pause
If the agent needs skills from a workspace not declared in the current workflow, the orchestrator pauses and asks. Outputs would mismatch the process.
Rule 3
Mismatch → new workspace
Rather than contaminate an existing workspace, spin up a purpose-built one with a merged workflow. Original workspaces stay clean.

Industry validation

How does this architecture compare to established patterns? Here's an honest assessment — what aligns with industry best practices, what's distinctive, and what gaps remain.

Aligned with industry standards

✓
Supervisor / worker pattern
The orchestrator-as-supervisor, workspaces-as-workers model is the most common enterprise pattern. Used by Microsoft Azure, AWS Bedrock, Google ADK, and LangChain as the default multi-agent architecture.
✓
Workspace isolation
Industry consensus: clear workspace isolation, defined file ownership, and explicit handoff protocols prevent conflicts. Our architecture enforces this structurally — each workspace owns its files and workflow.
✓
Context separation via subagents
Anthropic's own guidance emphasizes keeping detailed context isolated within sub-agents while the lead focuses on synthesis. Our workspace-scoped CLAUDE.md achieves this natively — each agent inherits only its workspace context.
✓
Simple composable patterns
Anthropic's building-effective-agents guide: "the most successful implementations use simple, composable patterns rather than complex frameworks." This architecture is pure files + SDK calls — no framework dependency.
✓
Skills as progressive disclosure
LangChain identifies this pattern: agent loads specialized knowledge on-demand. Our .claude/skills/ directories do exactly this — the agent discovers skills at session start based on workspace context.

Distinctively stronger than standard

★
Coherence invariant
Most frameworks talk about workspace isolation as conflict prevention. Our invariant is stronger: workflow and outputs must match. This isn't just about preventing file conflicts — it's about ensuring every output is governed by a workflow that accounts for it.
★
Declared vs undeclared reference detection
Most frameworks offer full access or full isolation. Our middle ground — declared refs are fine, undeclared refs trigger a pause — is more nuanced. It allows composition while preserving coherence.
★
Dynamic workspace creation
Spinning up a new workspace when a coherence violation is detected is a distinctive pattern. Most frameworks either force the task into an existing environment or require manual environment setup. Ours automates the decision.
★
Orchestrator as workflow-only entity
The explicit design that the orchestrator produces no mission outputs — only workflows, registry, and examples — creates a clean separation of concerns. Most frameworks let the supervisor also do work, which muddies the routing role.

Gaps to consider

⚠
Observability / logging
No mention of tracking agent interactions, token costs, or session histories across workspaces. Industry best practice includes communication logs and per-agent monitoring. Consider adding a shared log directory or event store the orchestrator can read.
⚠
Error handling / retry
What happens when a spawned agent fails mid-task? The current architecture doesn't specify fallback, retry, or partial-result recovery strategies. Frameworks like Temporal solve this with durable execution; Claude's Agent SDK has basic retry built in.
⚠
Cost management
Agent teams use approximately 7x the tokens of a single session. No mechanism for budget limits, model routing (Opus for hard tasks, Haiku for simple ones), or cost tracking per workspace. The Agent SDK supports model selection per spawn — worth codifying in the orchestrator's routing rules.
⚠
Workspace versioning
Dynamic workspaces accumulate. No strategy for archiving completed workspaces, tracking workspace lineage (which workspaces were merged to create this one), or cleaning up stale environments. Consider git-based versioning or a lifecycle policy.
Overall assessment: The architecture is sound and aligns with the industry's strongest patterns — supervisor/worker orchestration, workspace isolation, context separation, and simple composable design. The coherence invariant and cross-reference detection are genuinely novel contributions that go beyond what standard frameworks enforce. The gaps (observability, error handling, cost, versioning) are operational concerns you'd address when moving from design to production — they don't undermine the architecture itself.
